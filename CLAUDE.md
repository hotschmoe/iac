<!-- BEGIN:no-legacy -->
### No Legacy Code - Full Migrations Only

We optimize for clean architecture, not backwards compatibility. **When we refactor, we fully migrate.**

- No "compat shims", "v2" file clones, or deprecation wrappers
- When changing behavior, migrate ALL callers and remove old code **in the same commit**
- No `_legacy` suffixes, no `_old` prefixes, no "will remove later" comments
- New files are only for genuinely new domains that don't fit existing modules
- The bar for adding files is very high

**Rationale**: Legacy compatibility code creates technical debt that compounds. A clean break is always better than a gradual migration that never completes.

<!-- BEGIN:testing-philosophy -->
## Testing: End-to-End Only

**No unit tests and no TDD.** They weigh the codebase down. Verify with end-to-end tests: a real server, real clients over the real protocol, whole-engine scenario runs, the cross-language protocol fixtures, and the playtest harness. Do not add unit tests or module-level `#[cfg(test)]` cases, and do not delete existing ones without the owner's say (archive instead).

## Testing Philosophy: Diagnostics, Not Verdicts

**Tests are diagnostic tools, not success criteria.** A passing test suite does not mean the code is good. A failing test does not mean the code is wrong.

**When a test fails, ask three questions in order:**
1. Is the test itself correct and valuable?
2. Does the test align with our current design vision?
3. Is the code actually broken?

Only if all three answers are "yes" should you fix the code.

**Why this matters:**
- Tests encode assumptions. Assumptions can be wrong or outdated.
- Changing code to pass a bad test makes the codebase worse, not better.
- Evolving projects explore new territory - legacy testing assumptions don't always apply.

**What tests ARE good for:**
- **Regression detection**: Did a refactor break dependent modules? Did API changes break integrations?
- **Sanity checks**: Does initialization complete? Do core operations succeed? Does the happy path work?
- **Behavior documentation**: Tests show what the code currently does, not necessarily what it should do.

**What tests are NOT:**
- A definition of correctness
- A measure of code quality
- Something to "make pass" at all costs
- A specification to code against

**The real success metric**: Does the code further our project's vision and goals?

**Don't test the type system**: When writing tests, do not add cases for invariants or errors already enforced by the static type system (e.g., type mismatches, missing required arguments, nullability violations, return type correctness, enum exhaustiveness). The type checker handles these at compile time. Test solely runtime behaviors, business rules, algorithmic logic, and edge cases using only valid typed inputs.
<!-- END:testing-philosophy -->

### Project: In Amber Clad (IAC)

Multiplayer space strategy game with an amber CRT look. Humans play through the Flutter web client (`clients/web`), which is the primary interface. LLM agents play the same game directly against the engine's wire protocol as JSON (a WebSocket, or the headless NDJSON client). Both are first-class citizens, and a feature is done when the wire protocol and the web client have it. There is no terminal client: the ratatui TUI was retired on 2026-10-13 by the owner's decision, and its last state is in git history at the merge that split it from the headless client (`6c22e2d`, `clients/tui`). The live implementation is Rust; the Zig, full-stack Dart and Numen versions are on `archive/*` branches (see README.md).

```sh
cargo build --workspace
cargo test --workspace            # end-to-end tests only; retired unit tests live in the gitignored .archive/. Needs the wasm32-unknown-unknown target: solo/tests/both_targets.rs builds the browser engine
cargo test -p iac-solo --test both_targets   # the same worlds natively and as WebAssembly, reply for reply (about two minutes); run it after touching arithmetic, hashing, sorting or anything sized by usize
cargo test -p iac-server --test hosts_agree   # iac-solo loads the file a real server wrote; both must send the same frames, the rounds of a fight, the jump out of it under fire and a raid fought at home among them, and end with the same bytes (about a minute); run it after touching a host or the stored document
cargo clippy --workspace --all-targets   # also refuses std's powf, powi, ln, exp and their kin in shared, sim and solo
cargo run -p iac-sim --release --bin sim-run -- --pace season --days 7   # headless bot run, balance report with ships lost, fights fled, refuel deuterium and a table of how raids ended and what they cost (--seat, --sessions, --json; --defence-share scores the same world with defences at another share of their cost, which no world plays under; --outpost <ring>:<grade>:<level>[:<repairs>] stands an outpost for every bot at the start of day 3, which no bot founds, supplies, defends or hauls from, to measure its extractor, its raids and its store)

cargo run -p iac-server           # port 7777, world.iac, pace x1
cargo run -p iac-server -- --pace blitz --world blitz.iac   # pace and seed are fixed per world; --save-every <seconds> (default 300) is the most a killed server loses
cargo run -p iac-server -- --pace season --world season.iac --bot all:check-in --player-seats 8   # built-in bots, 8 of the 24 home seats kept for players
tail -n +2 world.iac | jq '.players | length'           # a world file is a header line, then the Snapshot as JSON
UPDATE_FIXTURES=1 cargo test -p iac-sim --test economy_numbers   # after changing an economy number: render docs/design/economy/numbers.json again (cargo test fails while it is stale)
python3 tools/check_sim_constants.py                    # after touching costs, times or production: the formulas sim.py keeps still agree with Rust
python3 docs/design/economy/sim.py --tables             # the planning simulation: --tables (about 16 s; its last table is the presets' two estimates, which shared/src/pace.rs copies), the full report with no flag (about 35 s), --set NAME=value to try a number before changing the game
cargo run -p iac-headless -- --name Agent   # the headless client: NDJSON on stdin/stdout

UPDATE_FIXTURES=1 cargo test -p iac-shared   # after a protocol change: regenerate fixtures/ and the Dart wire types (clients/web/lib/protocol/protocol.g.dart); then flutter analyze

cd clients/web && flutter pub get && flutter analyze && flutter test
scripts/play.sh                   # build web client + serve it and WS on one port (0.0.0.0:${PORT:-7777})
cargo run -p iac-server -- --host 0.0.0.0 --web-dir clients/web/build/web   # same, without rebuilding
scripts/play.sh --single-player   # static single-player bundle (client + iac_solo.wasm) in clients/web/build/single-player, served on 127.0.0.1:${PORT:-7777}; --no-serve only builds
cd clients/web && dart run tool/solo_e2e.dart   # that bundle end to end in headless Chromium, a flight, a fight and a raid on the homeworld included (about five and a half minutes; needs the bundle, and target/debug/iac-server for its multiplayer check; the world's seed is new each run, so the group it flees and fights is too, and at a blitz a group it hurt is whole again in four to nine minutes; it orders its first defence late, because an empire with a defence or a Shipyard at 2 is raided, and a raid that came while the world is passed four minutes at a time would be fought unseen with the docked fleet in it)
```

The server serves static files (SPA fallback, COOP/COEP headers) and WebSockets (any path; `/ws` for web, `/` for the headless client) on one port.

Flutter lives at `~/development/flutter/bin` on the dev machine. `flutter test` fails a fraction of full runs here, a different test each time, on values the client cannot compute (a NaN out of arithmetic on constants, an assertion inside Flutter's own layout or text code, an overflow of thousands of pixels), and one run has hung. The machine mixes Cortex-A720 cores (CPUs 0, 1 and 6-11) and Cortex-A520 cores (CPUs 2-5). A pin does not make the run reliable: CPU 0 failed 3 of 8 full runs, and `taskset -c 0,1,6-11` failed 9 of 25. `DART_VM_OPTIONS` does not reach `flutter_tester`, so a `--profile_period` set that way does nothing and the profiler stays on. Give the run `timeout -k 20 300`, keep its log, and run it again before reading a failure as the client's. The measurements are in `docs/design/flutter_test_flake.md`. The likely cause is this machine's own: its ARM kernel loses floating-point state around SVE (a C program with no Dart shows it), which a browser running the WebAssembly build and other machines do not share. The owner's decision of 2026-10-13 is to leave it alone for now: do not chase it, do not build a retry around it, and do not change the client for it.

### Architecture

```
Server (Rust, tokio)       Clients
  Tick loop (1Hz) --> WebSocket JSON --> Flutter web client (served by the same port): people
  world.iac       --> WebSocket JSON --> headless/LLM client (NDJSON): agents
  (one document)

Single player (one browser tab, no server)
  Web Worker: worker.js + iac_solo.wasm --> the same JSON, by postMessage --> Flutter web client
  wall clock -> ticks, IndexedDB (the same document)
```

- Server runs the authoritative simulation at 1 tick/second; clients send commands and receive `full_state` / `tick_update`.
- All rules live in `iac-sim`, which must stay pure: no tokio, axum, files, wall clock (`std::time`) or OS entropy (`sim/clippy.toml` bans clock reads). Time is ticks; every RNG is seeded from the world seed, tick or ids; entity maps are `BTreeMap` so passes walk in id order.
- A world is stored whole, as one document, and the engine knows nothing of it. Anything that must survive a restart goes in `Snapshot`, and nowhere else: there is no schema, no row, no dirty mark and no second list of fields to keep in step. A host takes `GameEngine::snapshot()` between two ticks, `iac_sim::store::encode`s it with its own part of the header (the single-player host's commander and clock; nothing for the server) and puts the bytes in its place (`Store`: `server/src/store.rs` over a file, `solo/web/worker.js` over IndexedDB); starting is `decode`, which refuses another `SAVE_FORMAT`, economy or generator and a document that fails its checksum, then `GameEngine::restore`. The two hosts store the same document, so `SAVE_FORMAT` is bumped when the header or what a snapshot must hold changes, and nothing is migrated. Do not put anything in the engine that exists for storage.
- What a stop costs is the hosts' to say, with `store::Due` (a document is owed a period after the last, or sooner once hurried, but never sooner than a short gap after the last). The server writes its file at every start once the bots are seated, every `--save-every` seconds (300), within `REGISTRATION_SAVE` (2 s) of the last write once a token was issued, and at SIGINT or SIGTERM. So a stopped server loses nothing; a killed one comes back as its last file says and loses at most the period, orders included, and a registration at most about three seconds. There is no journal of inputs (the owner's decision of 2026-10-13; `docs/design/storage.md` is how to add one). The tick only copies the world out; encoding and the disk are the `Writer` thread's. The single-player host saves every four minutes, two seconds after an order and every twenty seconds while catching up, and replays the ticks since its save on reload.
- A world plays the same on every target: the same seed and orders give the same bytes from a native host and from `iac_solo.wasm`. So float maths in `shared/`, `sim/` and `solo/` is written with what IEEE 754 fixes (the four operations, `sqrt`, rounding, casts) and, for everything else, with `iac_shared::maths` (`powf`, `powi`, `ln`, `log2`, `exp`, `exp2`: the `libm` crate and a fixed order of multiplication, never the platform's library); a function that module lacks is added to it. No `cfg` may pick arithmetic by target, and nothing may depend on the width of `usize` or on the order of a hash map. The `clippy.toml` of each of the three crates bans the std methods, and `solo/tests/both_targets.rs` plays the worlds on both targets and compares every reply. A change that moves what a stored world would play next bumps `ECONOMY_VERSION`.
- An amount is 64-bit. `Resources` is three `f64`, and so is everything that holds, carries, prices or sends an amount of a resource (stockpile, production, caps, holds, the outpost's store, salvage, loot, ore in the ground, costs, the exchange), a fleet's fuel and tank, and any constant or curve whose only use is to scale one (a share of a stockpile, a growth of a cap, `FUEL_DEUT_PER_UNIT`, `REFINE_LOSS`, `ResourceKind::weight`, the pace's multipliers). What is not an amount stays `f32`: power, odds, score and points, chances, a site's grade. Hull, shield and attack are whole numbers (`u32`, `scaling::unit_figures`, cut off as OGame cuts them), and a round is whole-number arithmetic from end to end. The two meet in named places and nowhere else: `scaling::resource_weight` narrows an amount to points; a 32-bit figure that scales an amount (a fleet's mass, a kill's farm factor, a roll) is widened with `f64::from` at that multiplication. Never narrow an amount to `f32` on its way between two 64-bit holders, and never change the type a random number is drawn as: that moves every draw after it. The line is recorded in `docs/design/decisions.md` ("amounts are 64-bit").
- A stored world, an order and a frame are JSON, and `serde_json` reads an `f64` back to the bit only with its `float_roundtrip` feature, which `shared/Cargo.toml` and `sim/Cargo.toml` turn on. Without it one `f64` in ten comes back a unit in the last place away and a restarted world plays on differently (`stored_world.rs`, `bots.rs` and the last test of `scenarios_world.rs` fail). Do not take it off, and read a number of the game from text with nothing less exact.
- Wire protocol types are written once, in `shared/`, and used by the server and the headless client. The Flutter client's are generated from them (`shared/tests/wire` writes `clients/web/lib/protocol/protocol.g.dart`), so a protocol change means: edit Rust, `UPDATE_FIXTURES=1 cargo test -p iac-shared`, fix what `flutter analyze` then points at in the app. Never type a wire key, a tag, a default or a `fromJson` in Dart, and never edit the generated file: `cargo test -p iac-shared` fails while it differs from what the Rust types generate. The generator reads the source, so it is held to serde: an attribute or type it does not know it refuses by name (teach `wire/model.rs` and `wire/dart.rs`, do not work around it), and `wire/samples.rs` round-trips messages made from its model through the real types. A label, a per-variant figure or a constant that Rust holds and the client needs is one line in `wire/mod.rs` that calls the Rust function or names the constant (an associated one as `Zone::INNER_RING_RADIUS`), not a second copy in Dart. `fixtures/` stays the end-to-end proof that the generated Dart reads and writes what serde does.
- A client draws and words; it does not work out a rule of the game. What a view of the web client shows comes, in this order, from the state the server sends, from a constant or a table generated from Rust (the bullet above), or from a field added to the state for it (`FleetState.jump_ticks`, the ticks one jump takes a fleet; `hops_home`, the fewest hops home over the real lanes; `FleetState.scan_range`). The catalogue is the largest case: what a building or a research does at its level and at the next is `effects` on its catalogue entry (`EffectKind`, `now`, `next`), what it waits on is `requires` (a `Requirement`, energy among them), what a ship or a defence is in a fight and in flight is on its `ShipOption` or `DefenceOption` with the owner's research in it, the energy is `HomeworldState.energy`, what opens the next building slot is `build_slot_unlock`, how many more of a limited defence may be ordered is `DefenceOption.room`, when a stockpile is full is `StorageState.full_in_s`, and the rapid-fire table is `WorldInfo.rapid_fire`. No formula of OGame's is written in Dart: the client gives a figure its unit and its words (`effectValue` in `lib/views/homeworld/spec.dart`) and never its value, and what the inspector says an item is needed by is read off the catalogue's `requires`. A fleet and a fight are the same case: a total a screen prints is the state's own (`FleetState.ship_count`, `hull`, `hull_max`, `attack`, `shield`; `PlayerState.ship_count`; `NpcFleetInfo.ship_count`; `HomeworldState.docked_ship_count`; a round's `BattleSide.entered`, `standing`, `shots`, `power`, `absorbed`, `hull_damage`, `destroyed`; a fight's `BattleState.losses` and `CombatEnded.losses`), never a sum over rows in Dart; what a dock would mend and why not is `FleetState.repair`, what a fleet fights with and that a refit waits is `refit` and `refit_due`, and what an odds label means is `RatioLabel.outcome`. Flight and pursuit are the same case again: what leaving a fight costs, the odds as it stands, who would follow and why the order would be refused are `FleetState.flight` (and `MovePreview.flight` for one lane, whose `chase` is absent where no group follows), a fleet that is leaving is `fleeing`, the group on its trail and whether it lands first is `pursued_by`, and a group's losses, its mending, its leash, its jump and its errand are on its `NpcFleetInfo`. The client compares no two jump times and counts no round; it prints the group's `jump_ticks` beside the fleet's and leaves the verdict to `flight.chase.rounds_per_hex` and `Pursuit.catches`. A raid is the same case once more, and the one most easily got wrong: how a raid would go is `RaidForecast.odds` (the label with `RaidLabel.outcome`, the three shares, `kept`), never one power against another. The client compares no two powers anywhere; the sums that stay on the wire (`home_defence_power` and its three parts, `next_raid_estimate_power`, an outpost's `platform_power`, `ships_power` and `defence_power`, `RaidResolved.raid_power` and `defense_power`) are read by no screen, and a `power` it does print (a forecast's, the range of a ring's raids) is a property of the force. Where a raid stands is the forecast's too: `rounds_left` while it is fought, `arrival_tick` while it is on its way, neither for one of typical size, so no screen looks in `battles` to learn what the raid is; the fight itself is the `battles` entry of the dock's sector (`GameState.raidAtHome`, `raidAtOutpost`), its defences a `BattleGroup` marked `battery`, and its ending is `RaidResolved` (`defended`, `outcome`, `lost`, `rebuilt`, `resources_lost`, `salvage_dropped`, `breached`), worded by `RaidEnding`. The rebuild's rule is printed from the three generated constants. A tick update's `battles` carry no `last_round`: the round is that update's `BattleRound` event, and only a full state carries the last round, for a client that arrives in the middle. The client orders a round's volleys for reading and for drawing and chooses how a mark stands for its count on the scope (`MarkShape`), which is drawing; it keeps no hull, no shield and no count of its own. A mark shows the state's figures or a round's, a count before a round is the round's own `entered`, never `count` and `lost` added, and what a scene holds back for the length of a beam is the figures it showed before, not ones it worked out. The rounds a battle view steps through are the ones the page was sent. A ratio of forces is an `f32` in Rust and is compared as one (`ratioLabelFor` in `lib/protocol/protocol.dart`); an amount is an `f64`, as a Dart number is, and is compared as it comes (`storageNearCap`). Either way an edge falls where the server's does. `WorldZone` in that file is the one place a ring is given its zone. Where the client must judge before the server can (a route planned over the chart), the figure says what was counted (`BY THE CHART`) and errs to the side the engine does not contradict. A literal stays in a view only as a drawing dimension. A refusal is the engine's sentence: a control is greyed on what the state shows, and anything else is sent and answered. `test/support/demo_world.dart` keeps to the engine's rules wherever a view shows them.
- A number of the economy is written once, in Rust (`shared/src/constants.rs`, `scaling.rs`, `pace.rs`, `sim/src/score.rs`). The planning simulation `docs/design/economy/sim.py` declares none: it reads `docs/design/economy/numbers.json`, which `sim/tests/economy_numbers.rs` renders and `cargo test` refuses when stale. Never type a number of the game into `sim.py` or edit the JSON. A number the simulation needs is named in Rust, added to the `named!` list of that test (or to one of its tables) and bound to a name in `sim.py`; a curve it only reads at whole rings, ratings or levels is rendered as a table by calling the Rust function. A number written out in `sim.py` is the simulation's own (the player model, the session schedules), except `zone_terrain` and `ore_prob`, a hand copy of what worldgen rolls. The file's `tables` half is what the Rust formulas give where `sim.py` computes for itself (a formula at any pace or score); `tools/check_sim_constants.py` compares those. Changing a number moves the game: the same rules about `ECONOMY_VERSION` apply.
- Only modified sectors are held (`Snapshot::sector_overrides`); unvisited sectors are generated from the world seed, which is why a world keeps the seed it was created with and the server refuses another.
- Built-in bots are ordinary accounts named `BOT-<personality>-<n>` that act only through the command path; their `BotRecord` lives in `Snapshot`. They are listed apart from the ranking (`LeaderboardReply.bots`). A pilot leaves a fight whose odds as it stands (`FleetState.flight.ratio`) are under RISKY, runs for home when pursued, and takes a wing with no warship into no fight (`bot::field::armed`): by the odds a hundred cargo ships beat a Battlecruiser and lose twenty of themselves doing it.
- An outpost is not a field of `Player`: `GameEngine::outposts` and `Snapshot::outposts` are keyed by the owner. Bots do nothing with outposts, and a world in which nobody founds one must play as it did before they existed.
- Hosting is written once, in `iac_sim::host`, and every host runs it: the server, `iac-solo`, the headless runner, and the tests that play a world with bots. One tick is `host::step` and nothing else: the cast's turns, `tick`, its events drained, every logged-in session's `tick_update`, the cast observes. One gate is `Host::receive`: a logged-in session's message goes to `GameEngine::answer`, `auth` goes to the `Door` and is followed by a full state, anything else from outside gets `commands::not_logged_in`. A host may differ from another only on two axes. Solo against multiplayer: the `Door` (`Tokens`, which registers and mints, or `Commander`, one name and no token) and the transport. Native against web: the clock and the place the document is kept, not the document. Do not write a tick loop, a session map, a login or a stored format in a host; if a host needs to look inside a tick, it gives `step` a `Watch`. `server/tests/hosts_agree.rs` holds the two real hosts to it: the single-player host loads the file the server wrote, and every frame and the bytes of the final world are compared. It cannot catch a change to the shared order itself, which moves both hosts together; `sim/tests/chart_equivalence.rs` and `bots.rs` do.
- `iac-solo` differs from the server only where one player and no network make it differ: no token (the world knows its commander), and a clock it is told (`now_ms` on every request), from which it owes one tick a second. More than 5 ticks behind is an absence: the missed ticks are played without frames, up to 7 days, then the session gets a full state and `Alert` events that report it. The save is the document a server stores, with the commander and the clock in the header's `host` part; ticks not yet saved are replayed on reload and must come out identical, so nothing but the commander's orders may enter a single-player world from outside.

### Key Concepts

- **Hex grid**: Axial coords (q,r), infinite, procedurally generated from `hash(world_seed, q, r)`
- **Zones**: Central Hub (0), Inner Ring (1-8), Outer Ring (9-20), The Wandering (21+)
- **Hub and exchange**: the centre sector is a neutral post (`world::HUB`, sent in `WorldInfo.hub`): no ore, hostile group, derelict or fight. Four roaming hubs stand in the Wandering and move (`docs/design/deep-space.md`, 3.3): `WorldGen::hub_sites` is the seed's choice of a sector for hub `id` in stay `epoch` (`scaling::hub_epoch`, `HUB_PERIOD_TICKS`), `GameEngine::hubs` the one the engine took at the stay's start that nothing blocked (`hub_blocked`: relay, outpost, group, fight), kept in `Snapshot`; a player learns of one by having eyes on its sector (`hub_sightings`, `GameState.hubs`, `HubArrived`, `HubDeparting`); they exchange through the same `exchange_terms` and `refuel` turns a hold into fuel (`refuel_deal`, `FleetState.refuel`), deuterium at the dock's rate and the rest through the exchange; `is_refuge` keeps pursuit out and no relay stands in one. Bots ignore them. A fleet standing there trades one resource in its hold for another (`exchange`, quoted first by `exchange_quote`); a per-player meter on the `Player` sets the fee, and the exchange never returns more than it takes. A hold is filled from the stockpile at the home dock by `load` (one resource an order, refused unless met in full) and stays aboard (`Fleet.laden`) until the fleet's next jump or `unload`; a lost raid counts cargo aboard fleets at home with the stockpile. Its four `EXCHANGE_*` constants are provisional and live in `shared/src/constants.rs`
- **Outposts**: one station per empire on a sector of rings 9 to 20, founded from what a fleet carries there (`found_outpost`; `outpost_survey` quotes a site and says why it cannot be founded now). One level, 1 to 3, sets its store, its platform and its extractor, which reads the ore the sector was generated with. It is a dock: `load` and `unload` there move cargo to and from its store, a fleet flown by hand is refuelled from that store and has its damaged ships mended from it (below, Damage), charts are banked, and a fleet standing there is not deployed; its sector holds no group while it stands. Pirates of its ring raid it on the homeworld's raid clock, and the raid is fought as the homeworld's is (below, Raids): the ships standing there and the platform, which is fixed defences for each level (`scaling::outpost_platform`) at the catalogue's figures and whole again after every fight. A lost raid has destroyed every ship that stayed, takes a quarter of the store above what the next repair would take, and breaches it until it has repaired itself from its store; a breached outpost has no platform, and a destroyed raid leaves no wreckage there. The repair is priced in metal and paid in whatever the store holds, metal first, then crystal at 1.5 and deuterium at 2 (`scaling::outpost_repair_payment`); the owner chose this over a repair that waits for all three resources. No raid destroys it. What a client would otherwise work out is the engine's to say and is in the state: why an upgrade would be refused now (`upgrade_refusal`, as `OutpostSurvey.refusal` is for founding), the least and the most a raid of its ring can be (`raid_power`), the yield a full store is losing (`yield_lost`), what a waiting repair lacks, counted in metal (`repair_waiting_for`), the defences its platform is and the forecast of the raid being fought, on its way or typical of the ring, with its ships and odds (`platform`, `raid`; `platform_power`, `ships_power` and `defence_power` are sums that decide nothing), that a fleet stands at it in any state (`FleetState.at_outpost`), and a threat rating of 0 for its sector; a survey of a sector never seen is a reply without `site`, not an error. Standing orders, bots and `recall` do not use it. Built on the recommendations of `docs/design/outposts.md`, whose six questions the owner has not answered (`docs/design/decisions.md`); every `OUTPOST_*` constant is provisional and lives in `shared/src/constants.rs`
- **Relays** (`docs/design/deep-space.md`, 3.2): a depot of deuterium on a sector of ring 9 or deeper, owner-only: `GameEngine::relays` and `Snapshot::relays`, a list per owner (`Relay`). No extractor, platform, repair, raid or garrison. Founded from a fleet's hold (`found_relay`; `relay_survey` quotes it; `relay_site` is the one place a founding is refused and worded, `scaling::relay_cost` grows with the ring), at most `scaling::relay_limit` of them (`RELAY_BASE_MAX` and a step per `RELAY_LEVELS_PER_STEP` levels of Hyperspace Technology). `load` of deuterium and `unload` there move the hold to and from its store (`RELAY_STORE`, not scaled by pace), and a fleet flown by hand is refuelled from it as it arrives, to `scaling::depot_fill_jumps` of its own burn (`GameEngine::depot_room`, which a roaming hub's refuel keeps to as well; `RelaysState.fill_jumps`) and as the store is stocked (`refuel_at_relay`, `process_relays`). A relay no fleet of its owner has landed at or moved a deposit at (`Relay::visited_tick`) for `RELAY_DECAY_TICKS` (attention class) is gone with its store; a fleet that stands there keeps nothing alive. A fleet in a fight is not refuelled there (`Depot`, `draw_tank`, which the outpost's dock shares). `relay_survey` of a sector the player has not seen says only that it is not on the chart. The state says it all (`GameState.relays`, `FleetState.relay`, the quote of `load` and `unload` with the engine's refusals); standing orders, bots and `recall` do not use one. Every `RELAY_*` constant is provisional and lives in `shared/src/constants.rs`
- **Edge pruning**: Connectivity decreases with distance, creating maze-like deep space
- **Catalogue**: the buildings (12), research (14), ships (13) and defences (8) are classic OGame's, with its names, costs, requirements, fight figures and rapid fire (`docs/design/ogame.md`, section 6; slice 1 of its section 12). `BuildingType`, `ResearchType`, `DefenceKind` and their formulas are in `shared/src/scaling.rs`, `ShipClass` and `Drive` in `constants.rs`. A number of OGame's is OGame's and is not tuned; what this game adds to a class or a research is a named provisional constant of the study's section 11 (`MAP_PAYS`, `JUMP_SPEED_REF`, `ShipClass::tank_jumps` and `harvest_power`, `TANK_PER_DEUT_TANK_LEVEL`, `FUEL_SAVING_PER_LEVEL`, `HARVEST_YIELD_PER_LEVEL`, `BUILD_SLOT_LEVELS`, `RECALL_SAVING_PER_LEVEL`, `SENSOR_HOPS_PER_LEVEL`, `NPC_POWER_BASE`, `RAID_POWER_FLOOR`, `RAID_POWER_PER_POINT`, `RAID_MIN_SHIPYARD`, `STARTING_SHIPS`). Hull in a fight is a tenth of OGame's structure. The curves in `1.1^level` are whole-number arithmetic (`scaling::tenth_curve`), because a float puts `ceil(10 x 1.1)` at 12. The fleet as counts and the fight are OGame's too (slice 2, below: Fleets, Combat, Damage). Flight, pursuit, pirates that mend and raids fought as battles are OGame's fight carried to this game's map (slices 3 and 4, below: Flight, Raids), in the engine and in the web client. The windshield draws all of it as a picture of class marks, and the battle view lists it (slice 5)
- **Energy**: the mines need it, the Solar Plant, the Fusion Reactor (which burns deuterium) and Solar Satellites make it, and it is not stored. Short of it, the three mines run at made over needed (`scaling::home_power`, `Power::fraction`); the natural production does not. `Player::production_per_tick` is net of the reactor's burn, `mined_per_tick` is gross and is what the exchange's span reads. A Solar Satellite is ordered in the shipyard as a ship, is a count on the `Player` (`satellites`), never joins a fleet, and stands in every raid's fight at home as a unit of it; those that fall are rebuilt as defences are, by the same rule and the same three constants (Raids, below), which is not OGame's and is the owner's decision of 2026-10-14. The state says all of it (`HomeworldState.energy`), and the web client prints it over the homeworld's plan and on the Overview (`EnergyReadout`) and as a share in the top bar
- **Resources**: Metal, Crystal, Deuterium (homeworld production, 20 metal and 10 crystal an hour of it with no mine, + active harvesting), each capped by its own building (Metal Storage, Crystal Storage, Deuterium Tank)
- **Pace**: one per-world multiplier (`shared/src/pace.rs`) scales economy timers; every duration constant declares a `PaceClass`. A pirate group's return and mending are finds timers (P^0.5, `scaling::npc_respawn_ticks`), as a derelict's return is
- **Score**: what an empire has built and keeps, recomputed from state (`sim/src/score.rs`): buildings + research + the ships it has now (Solar Satellites among them, so a fleet destroyed leaves the score) + the outpost's finished levels + defences at `DEFENCE_SHARE`, which is 0 (the owner's decision of 2026-10-14). Kills, charts and derelicts score nothing: a kill pays its wreckage (`WRECK_VALUE_K`, three times what it was when kills scored), a repelled raid its wreckage at home (`RAID_DEFENSE_SALVAGE_FRACTION`), a delivered chart `scaling::chart_value` into the stockpile at any pace (a `Stockpile` event of cause `Charts`), a derelict its loot (`RELIC_LOOT_MULT` times it with a relic). The board's row is the parts (`LeaderboardEntry`: `buildings`, `research`, `fleet`, `outpost`, `defence`); no combat or exploration points exist, and nothing in the engine is kept for the score
- **Fleets**: a fleet is a count for each class and the hull of each ship that is not whole, ascending (`engine::Ships`); a ship has no id and no record, and a shield is not stored. At most `MAX_FLEET_SHIPS` (5,000). `split` names classes and counts (`ShipCount`; whole ships first, or `damaged_first`), `merge` joins counts and damaged lists. What a fleet can do is summed from its counts by one function each in `engine.rs` (`fleet_jump_ticks`, `fleet_fuel_cost`, `fleet_harvest_power`, `fleet_fuel_max`, `fleet_cargo_capacity`, `fleet_power`). On the wire a fleet is one row a class (`ShipGroupState`) and its sums
- **Combat**: OGame's round (`docs/design/ogame.md`, section 7.1; `sim/src/combat.rs`), one a tick for each fight (`GameEngine::process_combat`): shields full, both sides fire at once, a shot picks one unit by a random index, a shot under a hundredth of the shield bounces, a unit with no shield left and its hull at `EXPLODE_BELOW_PCT` or under may explode, rapid fire by OGame's table (`scaling::rapid_fire_against`, sent whole in `WorldInfo.rapid_fire`). Whole numbers and dice of its own (`combat::Dice`, seeded from the world seed, the tick, the sector and the round, nothing stored), so a fight is the same bytes on every target and a world stopped between two rounds fights the next as it would have. Pirates fight by it with their ring's multiplier (`Arms::of_grade`). A fight in open space has no limit of rounds: it ends when a side is destroyed, when the last fleet has left, or when a round took no hull from anybody (`STANDOFF_ROUNDS`), after which both sides stay as they are. One `BattleRound` event a round and a fuller `CombatEnded`; no shot is an event. A round's rows say what stood in it when it began and what stands after it (`BattleUnits.entered` and `count`, `BattleSide.entered` and `standing`). The engine keeps a fight's last round (`Combat.last_round`, which is stored) and nothing of a fight that is over; `docs/design/decisions.md` (2026-10-14, the windshield as a picture) has what rounds weigh and what keeping them would take. `battles` in the full state and in every tick update is the fights a player is in, with the last round in a full state only: a tick update's round is its `BattleRound` event (a `Seat`, which is handed no events, reads its fights with `views::battles_of`). The odds are read off the same round (`odds.rs`): never write a second model of the fight, and when the round changes, measure `scaling::RATIO_MARGINS` again (the label scenarios of `scenarios_world.rs` say what each label must mean). Every knob of it is provisional and in `shared/src/constants.rs`
- **Damage, repair and refit**: damage to a hull lasts until a dock mends it. The home dock mends a fleet when it docks and every tick it stands there, for nothing (`REPAIR_COST_SHARE_HOME`); the outpost's dock mends whole ships, the most damaged first, for `REPAIR_COST_SHARE_OUTPOST` of a ship's cost times the hull restored, paid from its store by weight (`scaling::pay_by_weight`), and not when breached nor for a fleet under standing orders. A fleet fights at the Weapons, Shielding and Armour levels it last docked at home with (`Fleet.refit`, `Refit::arms`): research reaches it at the home dock, a split keeps them, a merge takes the lower of each, a recovered wreck takes the fleet's. The state says what a client would otherwise work out: `FleetState.refit`, `refit_due`, and `repair`, what each dock would do now and why it would not
- **Refining**: `refine` turns the deuterium in a fleet's hold into fuel, on the spot and at once, until the tank is full or the deuterium is gone, at `REFINE_LOSS` (0.15, provisional and the owner's) less than a dock's `1 / FUEL_DEUT_PER_UNIT`. Refused in combat and while a jump charges, and nowhere else; deuterium loaded at a dock counts, so a cargo ship is a tanker. `engine::refining` is the one place a hold's deuterium becomes a tank's fuel: the order, its refusal, the standing orders' switch and `FleetState.refine` (what the order would do now, absent when it would be refused) all go through it. Bots do not refine
- **Flight, pursuit and pirates that mend** (`docs/design/ogame.md`, sections 7.4 and 7.5): a `move` from inside a fight is flight. There is no fleet status for it: a fleeing fleet is `Moving` and still listed in its `Combat`, it stands in the round as a silent troop (`Troop.silent`), and it is out of the fight when `process_movement` lands it. A jump takes `max(1, ceil(JUMP_SPEED_REF / speed))` ticks at its slowest ship's speed (`scaling::jump_ticks`, linear in speed, so a fast fleet is something a player builds: a Cruiser on Impulse Drive 4 jumps in one tick and outruns the Outer Ring's pirates, which jump in two), and pirates' jumps follow the same law. A pirate group flies the heaviest of `NPC_LADDER` (Light Fighter, Heavy Fighter, Cruiser, Battleship) of which its ring's power makes `NPC_MIN_PACK` ships, so past the Inner Ring it is a pack that keeps the ships it has left. A fleeing fleet charges for `max(jump_ticks - 1, FLEE_MIN_ROUNDS)` rounds and pays `FLEE_FUEL_MULTIPLIER` jumps of fuel; `stop` puts it back in the fight. A fleet that is charging any jump when a fight starts around it keeps the jump and is in the fight the same way. A group that is not destroyed stays in `npc_fleets` as the fight left it (`NpcFleet.muster` is what it mends back to). When the last fleet has left, `begin_pursuit` sends it after the strongest that jumped out if it was beating it (`CHASE_MIN_RATIO`): `trail` is the one rule for whether a group follows (next door only, never into home ground, the hub or an outpost's sector, at most `CHASE_HEXES` jumps by behaviour before it has been home), `process_pursuit` runs between `process_movement` and `process_combat` so a group that lands fires the same tick, and its jump takes `scaling::npc_jump_ticks`. So a fleet as fast as its pursuer is never caught and a slower one is fired on for the difference at every hex; keep that order of the three passes. A fleet charges a jump in the sector it stands in, so "at once" means the order for the next jump reaches the engine before the tick after the landing: a tick later and a pursuer as fast as the fleet lands first and fires for that tick (`Pursuit.catches`). At rest in its own sector a wounded group mends a step every `scaling::npc_heal_step_ticks` (`NPC_HEAL_SHARE` of the respawn delay, a finds timer, in `NPC_HEAL_STEPS`); a fight or a pursuit stops the clock; whole again it is removed and the lair is its template (`settle_group`). Groups do not wander: nothing moves one but a pursuit and the way back. The state says what a client would otherwise work out: `FleetState.flight` (what leaving costs, the odds of the fight as it stands, the refusal, who would follow), `fleeing`, `pursued_by`, a hostile's `muster`, `whole_at`, `jump_ticks`, `chase_hexes` and `errand`, `MovePreview.flight`, `BattleGroup.fleeing`, `BattleOutcome::Fled` and the `Pursuit` event. `whole_at` is a tick, and the one figure of these a client turns into something else: a time from now. A sector out of sensor range is listed as it was last seen, its group with the losses and the `whole_at` of that tick, until a fleet sees it again. A remembered wounded group is rated whole once its `whole_at` is past (`remembered_opposing`). Every knob is provisional and in `shared/src/constants.rs`
- **Standing orders**: Per-fleet policy presets run by the server (`policy_update`), each with a range, an engage ratio and a fuel budget (`fuel_budget_pct` of deuterium income), and a switch, `refine`, off by default: a doctrine that would turn home for fuel refines the hold first and turns home only if that was not enough; every act and hold carries its reason (`PolicyAction`). A fleet under orders waits for no shield, and goes home to be mended before anything else when its hull is under `POLICY_HULL_READY`. In a fight it leaves once its odds in the fight as it stands fall below `disengage_ratio_x10` (default 9, never above the engage ratio; `policy_disengage`, one rule for every doctrine, reported as a `PolicyAction` `flee`), and with a group on its trail it runs for home first (`policy_pursued`). The web client's editor has it as its seventh setting and shows the server's clamp as the settings in force come back. Rules as players read them: `tools/playtest/RULES.md`
- **Raids** (`docs/design/ogame.md`, section 7.6): a raid is a fight, and the only place a defence fires. Its clock, its warning and its power (`scaling::raid_power_base`) are what they were. What it flies is fixed when it is announced, from the defences standing then (`scaling::raid_composition` over the knob table `RAID_WINGS`: Light Fighters, Cruisers once Rocket Launchers stand in number, Bombers once lasers and ion cannons do; an outpost's raid flies its ring's class, `outpost_raid_composition`). When it arrives it is a `Combat` with a `Siege` in it and no `NpcFleet`: no sector view, threat rating or pursuit knows the raiders. `siege_round` is one `combat::round` a tick, the raiders against the owner's fleets at the dock and the battery (at home every defence and Solar Satellite with the owner's research of that tick, written back to the `Player` after each round; at an outpost the platform), for at most `RAID_ROUNDS`. Three endings, in `end_siege`: no raider left (repelled, wreckage of `RAID_DEFENSE_SALVAGE_FRACTION` of their cost at a homeworld), the rounds over or a quiet round with a defender standing (`BattleOutcome::Outlasted`: repelled, nothing taken, no wreckage), no defender left (lost). `settle_raid` is the one place the ending is paid: at a homeworld the defences and the Solar Satellites that fell rebuilt at once at OGame's rate for defences (`rebuild_at_home`, `DEFENCE_REBUILD_PCT`, `DEFENCE_REBUILD_SPREAD` and `DEFENCE_REBUILD_EACH_BELOW`; the satellites are rolled for after the last defence, as a kind of their own, and are a row of `RaidResolved.rebuilt` while `structures_restored` stays the defences alone), and for a lost raid the skim above the protected share, the quiet after it, and the breach of an outpost. A raid that meets nothing is lost on the spot with no fight. A fleet at the dock is in the fight, may leave before it or flee during it by slice 3's flight, and nothing follows it. Nothing compares two powers: the forecast is the fight played forward (`raid_odds`, `odds::outlook_within`), and it is in the state as `HomeworldState.raid`, `OutpostState.raid`, `OutpostSurvey.raid` (`RaidForecast`: power, ships, `RaidOdds` with a `RaidLabel`). That forecast is the raid that matters now: the one being fought (`rounds_left` set, the odds from where the fight stands), else the one announced (`arrival_tick`), else one of typical size; a client or a bot that reads nothing else is never told there is no raid while one is fought. `BattleState.raid` says the same of the fight; a `BattleRound` and a `CombatEnded` of a raid carry `raid`, the defences are a `BattleGroup` marked `battery`, and `RaidResolved` says how it ended, what fell and what was rebuilt. Bots read the same forecast. `RAID_ROUNDS`, the raid's size and `RAID_WINGS` are the knobs, provisional, in `shared/src/constants.rs` and `scaling.rs`
- **Fading relics** (`docs/design/deep-space.md`, section 4): a derelict that rolls an ancient relic also puts an item aboard the boarding fleet (`Fleet.relic`, one, the stronger kept on a find or a merge, lost with the fleet), claimed on arrival at or recall to the owner's homeworld, finished outpost or relay (`claim_relic`). A claimed relic is one of six kinds (`RelicKind`: the three mines' output, fuel burn, research time, building time), held one a kind in `Player.relics` as `ClaimedRelic`, and gives `pct * (1 - elapsed / RELIC_FADE_TICKS)` read at the tick, never a stored figure. Each kind is one input of `RelicBonus` at the one place its figure is made (`scaling::production_per_tick`, `fuel_rate_modifier`, `research_time`, `building_time`); a family of kinds is held to `RELIC_TOTAL_CAP`. A relic never reaches the score, the exchange's span or the bots' planner. The wire has `PlayerState.relics`, `FleetState.relic` and the events `RelicFound`, `RelicClaimed`, `RelicFaded` (their kind field is `relic_kind`: `kind` is the event's tag)
- **Derelicts, scanning**: see the "The game" section of README.md
